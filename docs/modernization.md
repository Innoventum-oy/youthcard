# Youth Card modernization
version: 1.0
date: 2026-10-11

## Toolchain

- Flutter 3.47.1 / Dart 3.13.1; the project requires Flutter 3.47 and Dart 3.13 or later.
- Android: Gradle 9.6, Android Gradle Plugin 9.4, Kotlin 2.3.20, Java 17, compile SDK 37, target SDK 36.
- iOS: deployment target 15.0; validated with Xcode 26.5 and its iOS simulator SDK.
- `pubspec.lock` and `Gemfile.lock` are tracked to keep application builds reproducible. Private Git dependencies still require repository access.

The Android project uses the legacy Kotlin Gradle plugin compatibility flags generated by Flutter. Flutter reports that a future release will require migration to built-in Kotlin. The iOS build also reports an optional CocoaPods to Swift Package Manager migration. Neither warning currently prevents debug or simulator builds.

## Design

Editable mobile screen designs are in [Youth Card modern screens](https://www.figma.com/design/Qc215zClE0kqncDGYxF84I). They cover Welcome, Sign in, Dashboard, My card, Discover, Activity details, Calendar, Forms, and Settings.

The app now uses a shared Material 3 color scheme and navigation bar. It follows the device's light or dark appearance automatically, including themed fields, buttons, cards, navigation, and text. The Figma file contains editable light and dark variants of all nine screens with a two-mode color variable collection. Welcome, sign in, dashboard, card, discovery list, activity detail, calendar, forms list, and settings received direct layout work. Dynamic form fields inherit the new theme. The detailed Figma compositions still need visual QA with live content and translations.

## Core API and loading

GET requests use `core.ApiClient.requestJson` and multipart POST requests use `core.ApiClient.requestMultipart`, both with timeouts. Core prepares every attachment before sending and returns a typed response. Youth Card adapts `rawData` back to the legacy response maps expected by its existing callers. The older Core `postJson` attachment loop was also fixed to await each file.

The activity list cache now uses stable sorted request keys, a 30-minute fresh window, and an offline fallback. Activity details also fall back to stale data on request errors. Dashboard startup loads the saved user once; card, calendar, forms, and sign in now guard key async UI updates after disposal. A wider migration of legacy object providers and models to Core's object model would need endpoint-by-endpoint response tests against an iCMS environment.

## Local storage decision

Keep the existing JSON cache for now. The cached objects are small response snapshots keyed by request, with no local queries or relationships that would benefit from Hive CE indexes or adapters. Core includes Hive CE, so a future migration could reuse it if offline data grows. Moving the current cache now would add a data migration and web initialization path without a demonstrated speed or capacity gain.

The saved login record deserves a separate security review: it contains an API token in app documents. Hive CE alone would not encrypt it. If credentials are moved, use platform secure storage and migrate existing saved sessions carefully. Cache clearing deliberately preserves the saved user.

## Release

Run `bundle exec fastlane lanes` for the available screenshot and staged build lanes. The [Fastlane guide](../fastlane/README.md) covers device setup, screenshot naming, signing, and store credentials. Screenshot capture is guided: a reviewer navigates each screen and confirms it before capture. No store upload occurs during a candidate build. TestFlight and Play internal draft lanes perform uploads only when invoked with credentials.

Before publication, use a test account to review every Figma screen in the app, capture localized store screenshots at the required device sizes, run signed release builds, and check store listing and privacy requirements.
